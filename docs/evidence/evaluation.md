# Evaluation evidence

This records what was checked on the TenantLoom AI catalog evaluation, what was observed, and the limits of each result. The design is in [architecture section 11](../../architecture.md#11-mlops-and-evaluation) and [ADR-006](../adr/ADR-006-deployment-patterns.md); the model comparison itself is in the [catalog evaluation report](../../catalog/reports/catalog-eval-v1.md).

## Summary

| Check | Result |
|---|---|
| The evaluation service accepts the platform's locations | Verified: `us-east4` only |
| A judge model can score on the evaluation service | Verified, through an undocumented cross-region field |
| Catalog models answer in their documented locations | Verified for Gemini on `us` and Gemma MaaS on `global` |
| Held-out data is readable only by the evaluation account | Verified by design review and live IAM; see limitations |
| Dataset uploads match their committed manifests | Verified |
| The harness image builds and passes its tests in CI | Verified |
| An evaluation run traces from report to record to Experiments | Verified |
| Failed items are recorded without ending the run | Verified |
| The endpoint expiry job runs on its schedule | Verified, with nothing to expire |
| Full development runs for the managed models | Verified for all six |
| Full held-out runs for the managed models | One of six completed; five blocked by the provider |

| Model Armor floor settings screen evaluation traffic | Verified on `global`; not on `us` |

## Details

### Evaluation service and judge locations

- **Checked:** exact-match and judge-scored `evaluateInstances` requests on `us-east4`, `us`, and `global`, made in sandbox with a temporary Agent Platform User grant that was removed afterward.
- **Observed:**
  - Exact match returned scores on `us-east4`. On `us` the service answered "Unsupported region for Vertex Evaluation Service". On `global` the `gcp.resourceLocations` organization policy rejected the request.
  - Judge scoring on `us-east4` failed with both the default judge and `gemini-3.8-flash`, because neither is served there.
  - With the `v1beta1` request field `allowCrossRegionModel` set and the judge named on `global`, the service returned a score and an explanation.
- **Significance:** the evaluation service runs in `us-east4`, and the support rubric's judge runs on `global`.
- **Limitation:** `allowCrossRegionModel` does not appear in the public API reference and may change. The fallback is to score the rubric in the harness with a pinned judge on `us`.

### Model locations

- **Checked:** `generateContent` calls as the model test account.
- **Observed:** `gemini-4-argon` answered on `us`. `gemma-4-26b-a4b-it-maas` returned not found on `us` and `us-east4`; on `global` it was first refused by the model allowlist, which named the exact allowlist value, and once the catalog added that value it answered.

### Held-out data isolation

- **Checked:** the IAM on both dataset buckets and on the nonprod project, and the Agent Platform service agents' project-level roles.
- **Observed:**
  - A review found that sandbox's Agent Platform service agent holds project-wide object read, and that Agent Platform User lets a caller start workloads that run as that agent. A held-out bucket in sandbox would therefore be readable by anyone able to deploy there. The held-out bucket was moved to nonprod before any data was uploaded.
  - In nonprod, no person or workload holds a role that can create Agent Platform workloads.
  - On the held-out bucket, the evaluation account holds object read and create; platform administrators hold object create only, which can upload but not read.
  - Each run's report is written next to the split it read, so held-out reports stay in the held-out bucket.
- **Limitations:**
  - The break-glass account cannot read bucket IAM policies, so the bucket grants were confirmed from the reviewed plan and the apply log rather than read back independently.
  - Two accepted exceptions also reach held-out data: the legacy Cloud Build service account in nonprod and the inherited folder administrator (ADR-004).
  - Nonprod's Agent Platform service agent can read every bucket in nonprod, so this isolation holds only while no identity in nonprod can start Agent Platform workloads.

### Datasets

- **Checked:** generation, split, upload, and hash comparison for `docs` and `support` v1.
- **Observed:**
  - The invoice set is generated by a seeded program whose labels come from the values it renders, so they are exact. The support tickets and reference summaries were written by `gemini-4-argon` and reviewed by a person before upload; one reference was corrected, and two email addresses were moved to reserved `.example` domains.
  - Uploads used create-only requests, which cannot replace an existing object. For all four files, the MD5 returned by Cloud Storage matched the manifest, and the local files matched the manifests' SHA-256 and item counts. No item appears in both splits.
  - The manifests in `eval/datasets/` hold counts and hashes only.
- **Limitations:** the people who generated and reviewed the data have seen the held-out items. The support data was written by one of the evaluated models.

### Harness image

- **Checked:** the `platform-eval-image` build that followed the manifests merge.
- **Observed:** the build ran as `sa-eval-build`, passed the unit tests, and pushed `eval-harness@sha256:54eb1c9b4e395965dcce553a479c1c96f76228e70e0a91b82307ab0c5e13d089` to a repository with immutable tags. The base images are pinned by digest, and the evaluation job is pinned to this image digest.

### A traced evaluation run

- **Checked:** a three-item run of the docs task with `gemini-3.8-flash`, started by a platform administrator with argument overrides.
- **Observed:**
  - The custom `evalJobRunner` role was enough to start the job with overrides.
  - The record holds the dataset hash matching the manifest, the model, location, generation parameters, prompt version, image digest, harness commit, metrics, thresholds, the report location, and the Experiments run, which the job's log shows was attached to the `default` metadata store in `us-east4`.
  - Because of the item limit, the record shows `passed = false`, as designed.

### Development runs

- **Checked:** the docs and support tasks for `gemini-3.8-flash`, `gemini-4-argon`, and `gemma-4-26b-a4b-it-maas`.
- **Observed:** all six completed with no item errors; results are in the [catalog evaluation report](../../catalog/reports/catalog-eval-v1.md). Every model scored full accuracy and the maximum rubric score, and only the MaaS model met the latency target.
- **Limitation:** the v1 datasets are too easy to separate the models by quality, and the judge has not been tested against deliberately poor summaries.

### Held-out runs and the provider block

- **Checked:** the same six runs on the held-out split, then direct `generateContent` calls and a console prompt.
- **Observed:**
  - The Gemma MaaS docs run completed. The other five recorded every item as failed.
  - Direct calls to `gemini-3.8-flash` and `gemini-4-argon` in sandbox, on both `us` and `global`, returned HTTP 403 with "Request rejected in accordance with our terms of use and policies." A console prompt in sandbox returned the same. The same call in nonprod succeeded, `countTokens` in sandbox succeeded, and Gemma MaaS in sandbox kept working.
  - The block was still in place in retests about an hour later and about fifteen hours later. No notice explaining it was found in the console.
  - Before the block, six evaluation runs had been started at the same time.
- **Significance:** the failed runs show the harness recording failures per item instead of producing a false result. The block stayed within sandbox, which is why evaluation runs in its own project.
- **Limitations:** the cause is not known. Evaluation runs are now started one at a time.

### Model Armor floor settings

- **Checked:** the Model Armor monitoring view in sandbox.
- **Observed:** the floor setting screened 610 Agent Platform interactions on `global`, flagging 12 and blocking none, since sandbox only inspects. None of the calls on `us` appear. The `baseline` template recorded the one sanitize call made against it.
- **Significance:** floor settings apply to Agent Platform calls on `global` but not on `us`, which refines the [governance finding](governance.md#model-armor-floor-settings). Model Armor did not cause the provider block: the block also covers `us` calls that Model Armor never saw, and Gemma MaaS on `global` kept working through the same floor setting.
- **Limitation:** which filters flagged the 12 interactions is in the restricted Model Armor log bucket, which was not queried.

### Endpoint expiry

- **Checked:** the first scheduled run of `endpoint-expiry`.
- **Observed:** Cloud Scheduler started the job through the Cloud Run Admin API as `sa-model-deploy`, and it exited successfully with no deployments to undeploy.
- **Limitation:** undeploying an actual expired deployment has not been observed.

### Review of the harness and its infrastructure

- **Checked:** an independent review of the Terraform and the harness before the first apply, with each finding checked against live role definitions or the SDK source.
- **Fixed before apply:** held-out reports in a readable bucket, the held-out bucket in sandbox, credentials sent to any endpoint URL, mutable image tags, broad table permissions for the evaluation account, Experiments creating a TensorBoard, a single failure losing a whole run, colliding run names, limited runs recorded as full ones, unvalidated judge scores, and an expiry job that stopped at its first error.
